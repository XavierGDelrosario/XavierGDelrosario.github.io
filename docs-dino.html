DINO 大脳 · Design & architecture notes

DINO — Japanese Vocabulary Trainer

Documentation for a Japanese ↔ English vocabulary-learning app — the tokenization pipeline, the trust boundary between browser and server, and the operational choices that keep the live app available while it evolves.

Overview

  • A vocabulary-learning app for Japanese ↔ English: translate a single word or a whole sentence, save what you find to lists, and review it with spaced-repetition flashcards.
  • One input decides everything — an in-browser tokenizer classifies the text as a word (show every sense) or a sentence (render a word-by-word reader), with no manual toggle.
  • Ships as both a web app and a native iOS build from a single codebase.

Architecture

  • Frontend — Vite + React 18 + TypeScript; plain hooks and CSS, no router or state library.
  • Backend — Supabase: Postgres with row-level security, Auth, and a Deno edge function (translate) that is the only place translation happens.
  • Dictionary — a self-hosted JMdict corpus, with Google Cloud Translation as the fallback for words JMdict lacks and for whole-sentence glosses.
  • Japanese NLP — kuromoji runs in the browser for segmentation, readings, and lemmatization.
  • Native — Capacitor wraps the web build into an iOS app.

Design choice · Separate staging and production databases

The choice the rest of this page builds toward: never make the live database the test bed.

  • Two isolated Supabase projects. Production and staging are entirely separate databases, each provisioned identically — same migrations, same data ingests, same edge function.
  • Every change flows staging → verify → prod. Risky work — a schema migration, an edge-function change — is applied and proven on staging first, so a bad migration can only take down a throwaway environment, never disrupt the availability of the live app.
  • The environment is selected, not edited. Deploy scripts pick a target from a DINO_ENV variable pointing at separate credential files (.env.deploy vs .env.deploy.staging), so there is no hand-editing of connection strings and no chance of pushing a test change straight to prod.
  • It doubles as the device test bed. An iOS build running on a real device can't reach the developer's local machine, so on-device testing points at staging — keeping unverified builds off production data.

Other design choices

  • The trust boundary decides where code runs. Translation runs only on the server (an edge function holding the service role; RLS forbids any client from writing a verified translation), because cached translations are trusted data that need a single privileged write seam. Morphological analysis runs in the browser, because it feeds an ephemeral, display-only reader — nothing it produces is persisted, so there's no trust boundary to defend and it avoids a round-trip per keystroke.
  • Reserve-before-call quota. Paid translation calls are metered against a monthly cap. Rather than "check usage → call → increment" (a check-then-use race where two concurrent requests both overshoot and cost real money), an atomic RPC checks and increments under a per-user lock before the paid call — so a denied request costs nothing and concurrency can't slip through.
  • Reading resolution routes by context. A homograph reads differently by context (辛い → からい "spicy" / つらい "painful"). Isolated lookups use the dictionary's authoritative stored reading; in a sentence, kuromoji's context-aware reading wins — overridden by the dictionary only when the surface is the dictionary form and its senses agree on one reading.
  • Getting kuromoji into the browser. Two non-obvious Vite fixes were load-bearing: aliasing Node's path to a shim so kuromoji's loader doesn't silently fall back to Intl.Segmenter (no lemmas), and serving the dictionary .dat.gz files as raw bytes so the browser doesn't auto-decompress them out from under kuromoji's own gunzip.

Testing & delivery

  • Service-layer unit tests with Vitest, plus an integration suite that exercises row-level-security policies against a live instance.
  • CI runs typecheck, lint, and tests on every push, and boots a Supabase instance to run the RLS integration job.
  • Cost is capped in the edge function itself — a global monthly character quota with an emergency kill-switch that falls back to dictionary-only lookups without a redeploy.
