DINO 大脳 · Project summary & engineering notes

DINO — Language Learning App

A Japanese ↔ English vocabulary app. You paste in text you encounter — anime subtitles, a news article, a transcript — and it breaks the Japanese into individual words, color-codes them by how well you know each one, lets you save any word with one tap, then quizzes you later with spaced repetition. The differentiator: it reads what you pasted, works out the topic, and suggests related vocabulary from that topic at your level. Live on the web, with a native iOS build adding handwriting, speech, and camera input.

Highlights

  • Shipped a full-stack app solo in five weeks. React 18 + TypeScript frontend, Supabase/Postgres backend with row-level security, Deno edge functions, a native iOS build via Capacitor with three hand-written Swift plugins, and five Python/Node data-ingest pipelines — across 178 commits and 37 reviewed pull requests.
  • Reduced translation API cost to near-zero. Self-hosted a 217,000-entry Japanese dictionary plus a semantic WordNet layer inside Postgres, demoting the paid Google Translation API to a fallback for cache misses only — then made overspend structurally impossible with atomic reserve-before-call quota accounting, per-user and always-on global monthly ceilings, request idempotency so retries cost nothing, and an environment-flag kill switch.
  • Ran a statistical study before trusting a core heuristic — and let the data overrule the plan. Measured corpus frequency against curated JLPT levels across 7,523 words (R² = 0.24; 14.7% misread as ≥2 levels too easy), found the error structurally biased by part of speech, tested the intuitive fix and found it blew the dangerous-error rate from 0.9% to 15%, and shipped an asymmetric correction instead.
  • Built the differentiator — a level-matched semantic word map. Embedded ~41,000 entries into Postgres pgvector, exposed nearest-neighbor search through a permission-gated function, and expand a pasted text into the vocabulary around its topic — ranked by domain centrality and filtered to ±1 of the user's calibrated level.
  • Diagnosed a silent production failure that corrupted results. Traced a blank word-reader to a 7 KB request URL the runtime refused to send — caused by duplicated lookup keys at ~9 encoded bytes per Japanese character — then chunked requests by encoded byte size and verified 156/156 words resolving with zero duplicates and zero API spend across local, staging, and production.
  • Fixed three interacting spaced-repetition defects by measurement, not intuition. Cohort clustering (hundreds of identically-seeded words flooding every session), mature lapses rescheduling half a year out, and daily cramming inflating an interval 40→85 days on evidence that only ever proved one-day recall — each verified numerically after the fix.
  • Owned the full production lifecycle. Branch-protected main with four required CI gates, a separate staging environment, secret scanning over full git history, encrypted off-host scheduled backups with an automated restore test, a phased deploy script with an explicit CORS-lockdown step, and a post-deploy smoke check asserting unlisted origins are rejected.
  • Architected for a second language from day one without over-building for it. Language is part of every identity key, readings are two-sided and nullable (kana / pinyin / romanization), and each dictionary sits behind a provider seam — reducing "add a language" to a 50-checkbox documented checklist rather than a schema migration.

Deep dives

01The difficulty-signal study — knowing when not to trust your own feature

To retire a word from review once you clearly know it, the app needs to know how hard it is. Curated JLPT levels are reliable but cover only 3.4% of the dictionary; corpus frequency covers far more. The tempting move is to use frequency as a stand-in for difficulty — so I measured it first. Across 7,523 words carrying both a JLPT band and a frequency score: r = −0.489 (R² = 0.24), exact-match 31.5%, within-one-level 78.2%, and 14.7% reading ≥2 levels easier than they are — the dangerous direction.

The errors weren't noise; they were structured. Frequency is counted per written form, so a verb's usage splits across dozens of conjugations (食べる doesn't count 食べた / 食べます) and looks rarer; affixes and counters never conjugate and look far more common. Measured against each word's own band: affixes +0.60 Zipf too easy (31.3% dangerously misread), verbs −0.76 too hard (0.9% misread) — different bias, not different noise, and bias is correctable. Correcting every class toward its band improved the headline metric (MAE 0.96→0.85) but broke verbs, blowing their dangerous-error rate to 15%. Because the costs are asymmetric — wrongly retiring a word hides it forever; wrongly reviewing one is nearly free — I shipped a correction that may only ever nudge a word harder, capped the interval multiplier by signal quality (2.5× from a curated band, 1.6× from frequency, 1.0× for an unmeasured language), and shipped the recall-logging columns before the feature that will eventually settle it properly.

Why it matters: most engineers ship the heuristic. This one measured it, found it weak, found why, tested the obvious fix, rejected it on the metric that actually mattered, and capped the feature's authority to match the evidence.

02The differentiator — a semantic word map, level-matched

Batch-embedded ~41,000 dictionary entries into Postgres pgvector with a multilingual model, exposed nearest-neighbor search through a permission-gated function so raw vectors never leave the server, and used it to expand a pasted text into the vocabulary around its topic. Two design points carry the feature: candidates are ranked by domain centrality (how many of the text's words a candidate sits near) rather than raw similarity, and the two axes stay strictly separate — embedding distance encodes relatedness, frequency encodes difficulty, so candidates are retrieved semantically then filtered to ±1 of the user's calibrated level. Level estimation is deliberately conservative (a level must clear 75% recall to be credited) because under-rating a learner just shows a word more often, while over-rating hides one they needed.

A limitation was documented honestly rather than shipped silently: katakana loanwords cluster by spelling, not meaning, under the small model — ストライカー "striker" → ストリーカー "streaker" at distance 0.026 while the genuinely related ピッチャー "pitcher" ranked last. I traced the cause (subword overlap on both surface and gloss), identified its signature (0.03–0.06 distances, far tighter than real synonyms), and scoped the real fix as a deliberate deferral. It also drove a shipped safety feature: a content filter applied to suggestions only, never to direct lookup.

03A self-healing dictionary cache — invalidation that never fires a re-bill

Every cached dictionary row carried a projection_version stamp, bumped whenever the projection logic improved. It had been written faithfully for weeks — and read by nothing. Against production, 4,685 of 4,953 cached rows sat on outdated versions, still serving pre-fix results (including an old sense-ordering bug — the wrong primary meaning, permanently) for exactly the words people had already looked up. Deleting stale rows breaks saved words (the foreign key nulls out and fails a not-null constraint); re-inserting forks rows, because the headword itself is a projection output a logic change can move (いく → 行く). The fix: treat a below-current version as a cache miss so the stable-identity key updates the row in place — same row ID, saved words never dangle, cache heals as words are used — with paid-API rows explicitly exempted so a version bump can't re-bill, gated in both runtimes with a drift test.

04Tuning the spaced-repetition model against real review data

  • Cohort clustering. The placement quiz writes hundreds of words with identical starting strength at one instant, so they shared a decay curve and flooded every session as one block. Fixed by jittering every strength write; verified 60 identically-seeded words now spread across ~35 days. The randomness is load-bearing and documented as such so nobody "cleans it up."
  • Cram inflation. 14 days of perfect daily reviews took a word 40→85 days — the model claiming 84% recall at a two-week gap from a learner who'd only ever proven one-day recall. Fixed by freezing interval growth on a successful review of a still-fresh word, with failures exempt so daily study still rehabilitates words you're forgetting.
  • The review deadlock. Once a user cleared their whole vocabulary, every word was fresh, the freeze meant nothing moved, and the queue served the same three words for four straight sessions. Fixed with a two-phase queue — genuinely-due words first, then a filler mix weighted toward low-confidence words with rare cameos from mastered ones.
Why it matters: three bugs no test suite would catch, because each produced plausible behavior. Each was found by instrumenting the model and checking whether its claims matched the evidence it had.

05Reversing a plan when the data disproved it

The entire difficulty axis was originally designed around JMdict's built-in priority tags. Before building on them I checked whether they were actually present — and grepped the full 217,000-entry dataset for zero hits (the tags are collapsed to a single boolean by the distribution format, in both editions). The parser had shipped that same day; it was replaced within hours by a wordfreq pipeline that ranks on the headword's frequency, not the max across readings (a shared kana reading would otherwise inflate an unrelated word). A related scope call: I proposed trimming the dictionary by frequency to save storage, then verified the tokenizer can't rank multi-kanji compounds at all — so the filter would have silently deleted an entire word class. The dictionary stayed full; the frequency floor applied only to the embedding set.

06Cost, licensing, and legal — treated as engineering problems

  • A named threat model. "THE LOOPHOLE": the spend quota is per-user, but anonymous sign-in mints users freely, so a rotating-IP bot gets unlimited quotas. Answered with an always-on global ceiling (deliberately no "uncapped" setting), an invisible CAPTCHA on the three account-creation endpoints, a bounded sweep of empty guest accounts, and hard billing caps at the vendor.
  • A bounded destructive operation. The guest sweep is anonymous-only, empty-only, aged on two clocks, skips anyone with current-month paid usage, is capped per run, audits every removal, and is dry-run-first — proven with a 9-case test asserting a guest with a word, a guest with a list, a recent guest, a spender, and a real account all survive.
  • A six-dataset commercial licensing audit against a stated standard (commercial use / redistribution / attribution / share-alike), with a "rejected — must not ship" section naming three otherwise-ideal but legally unusable datasets; plus a deep-research pass on proficiency data (17 sources, 25 claims adversarially verified, 21 confirmed / 4 refuted and recorded).
  • A vendor-exit analysis with a number attached: a per-layer portability table, five ranked exit triggers, and the conclusion "~70% of backend work survives an exit. We are not trapped."

07Native iOS — scope managed without leaking into the architecture

Three input modalities shipped on iOS with hand-written Swift plugins — handwriting (draw a kanji you can see but can't type), speech-to-text, and camera OCR — all free, on-device, and offline, versus paid cloud APIs on web. The platform work is genuinely specific: a custom-scheme PKCE OAuth flow that completes the token exchange inside the same WebView (the standard redirect escapes to Safari and never returns) plus a cancel listener so the UI can't hang; custom re-ranking of machine-vision output (the handwriting engine ranks punctuation above simple characters; OCR returns blocks in unreliable order, re-sorted for horizontal text with vertical writing documented as a known gap); and a multi-stroke timestamp fix (timings were per-stroke, resetting to zero each time). iOS-only was a cost decision written down as delivery scope only: every provider sits behind a registry seam whose availability check returns false on web, so views hide the affordance with no branching — "so a temporary cost decision never hardens into a design constraint."

Testing — five layers, 1,600+ cases

Each layer covers what the layer below structurally cannot. 1,600+ cases across 69 files, 10k LOC of test code — a 0.54 test-to-source ratio.

LayerWhat it proves
Unit (393)Pure logic — difficulty calculator, filter matcher, kana-only search gate, domain ranking, level estimator, forgetting curve
Component / hook (74)React behavior via Testing Library and renderHook
Cross-runtime (81)The Deno edge function's pure logic, extracted to a shared module so Node can test it
Integration (135)Real booted Postgres + a live-served edge function — security policies, constraints, stored procedures
End-to-endPlaywright against the real production bundle in a real browser
  • Know what each layer can't prove. The unit suite mocks the database, so it verifies intent only — that the client sends the right flag, not that the database would reject a violation. That gap is documented; the integration suite exists to close it.
  • Assert specific error codes, not "it threw." Constraint tests assert exact SQLSTATEs, so a dropped constraint fails the test instead of passing vacuously.
  • Test security adversarially — two real users, cross-user isolation on every table, the dictionary proven read-only to clients, privileged functions proven to reject cross-user calls, and a live-verified case where local permissive defaults masked a real production leak.
  • Guard whole bug classes, not instances — a missing-glyph bug produced a test scanning all UI source for text-default emoji; cross-runtime constants have a drift test; both were verified by re-introducing the regression.
  • Distinguish flake from failure — CI retries only the integration suite, only on PRs, after a duplicate-run config once let a flaky run block merges; the readiness probe POSTs a real payload and waits for a genuine 200.
  • Verify backups by restoring them — a scratch database is built from a live schema dump, the backup replayed, and every table's row count asserted against live. Tests arrived on day 5 of 37; 34% of all commits touch tests/.

Project management & process

  • Prioritized by launch-blocking, not by interest — a tiered backlog re-cut as work landed, item numbers preserved so external references don't rot, and the project's own headline feature explicitly demoted to "a feature not a gate."
  • Sequenced by cost-of-delay — "data-model decisions first, cheap before real users have saved data, painful after"; the roadmap is dependency-ordered and the differentiator is built last, on data the earlier steps already proved.
  • Every deferral names its trigger — not "later" but gated on a test harness for the destructive path, on the second language shipping, on review volume existing to fit the curve against.
  • Decisions written in a reusable format — a 16-fork design log (fork → what most people would do → what we did and why → what it demonstrates), including falsified plans and one explicitly reversed decision; documentation genres (research / audit / roadmap / decision log / runbook) each have a README defining what belongs.
  • Formalized workflow 12 days in and held to it — protected main, every change through a branch and a PR with four required checks, squash merges, median PR ~190 lines across 5–7 files, 20 of 26 merged same-day.
  • Commit messages as engineering artifacts — 95.5% conventional, 98% with a body shaped as symptom → root cause → fix → trade-off → verification, with honest labels when something is not yet verified.
  • Audited the project's own construction method — a checklist of characteristic failure modes for an AI-assisted codebase ("each one we actually hit this project"); a 37-agent pre-publish review found 11 issues, all fixed, and re-running it is now a standing release gate.
